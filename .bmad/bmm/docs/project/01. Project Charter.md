# 🚀 PROJECT CHARTER (V2): SchoolBridge LMS

## 1. Project Overview

**Project Name:** SchoolBridge Learning Management System (LMS)

**Tagline:** "Your Complete, Connected, and Resilient Educational Ecosystem."

**Vision:** To evolve SchoolBridge from a communication tool into a comprehensive, offline-first Learning Management System. We aim to provide a resilient and accessible educational ecosystem for schools in any environment, with a special focus on empowering communities with limited or intermittent connectivity.

## 2. Project Objectives & Success Metrics

### Primary Goals
- **Empower Educators:** Provide a powerful, intuitive platform for instructors to create, manage, and validate rich, multimedia course content.
- **Engage Learners:** Offer students a flexible and engaging learning experience with diverse content types, detailed progress tracking, and full offline access.
- **Connect Stakeholders:** Strengthen the connection between students, teachers, parents, and administrators through dedicated profiles and enhanced communication channels, including contextual messaging.
- **Bridge the Digital Divide:** Implement a revolutionary offline-first architecture with local school servers to ensure uninterrupted access to education, regardless of internet availability.
- **Ensure Quality & Consistency:** Establish a formal course validation and versioning workflow to maintain high educational standards.

### Success Metrics
- **System Resilience:** Achieve 95% core functionality (course consumption, progress saving) on both the local school network and offline-enabled client devices.
- **Content Accessibility:** All course content variants (video, articles, quizzes) are downloadable and available for offline use, with user-configurable quality settings.
- **User Adoption:** Achieve 80% active weekly usage across all user roles (Student, Teacher, Parent) within the first 6 months of a pilot deployment.
- **Performance:** Maintain sub-3-second page loads for critical paths on the local network and demonstrate successful, non-blocking data synchronization with the cloud.
- **Data Integrity:** Ensure a <1% data conflict rate during cloud synchronization from local servers and client devices.

# 3. Scope & Boundaries

## IN SCOPE (Phase 1 - LMS Implementation)

### User & School Management
- **Multi-Tenancy:** Full separation of schools, each with its own users, courses, and classes.
- **Granular User Roles:**
    - **Student:** Enrolls in courses/classes, consumes content, tracks progress, takes quizzes, submits assignments, and manages offline content.
    - **Parent:** Monitors children's progress, grades, and teacher communications.
    - **Instructor:** Creates and manages courses, lectures, assignments, and grades.
    - **Educational Manager / Content Moderator:** Reviews, validates, and approves course content.
    - **School Admin:** Manages school settings, users, classes, and academic periods.
    - **Super Admin:** Oversees the entire platform.
- **Academic Structure:** Management of Academic Periods (e.g., terms, semesters) and Classes within a school.

### Core LMS Features
- **Comprehensive Course Management:**
    - Creation of courses with detailed metadata (title, description, level, language, objectives).
    - **Course Content Structure:** Courses composed of Sections, which contain Lectures.
    - **Diverse Lecture Types:** Support for Video, Articles, Quizzes, Coding Exercises, Assignments, and Projects.
- **Content Validation & Versioning:**
    - Formal workflow for course review and approval (`CourseValidation`).
    - Versioning system for tracking course updates (`Version`).
- **Assessment & Grading:**
    - **Quizzes:** Multiple question types, time limits, attempt tracking, and automated scoring.
    - **Assignments:** File submissions, due dates, and manual grading with feedback.
    - **Centralized Grading System:** A unified `Grade` model to track student performance across all gradable items.
- **Progress Tracking:**
    - Detailed, per-lecture progress tracking for each student (`LectureProgress`).
    - Course-level completion percentage and time-spent calculation.

### Offline-First & Local Infrastructure
- **Local School Servers:**
    - **On-premise servers** (`SchoolServer`) within schools to act as a local content cache and data hub.
    - **Content Caching:** Intelligent caching of course materials (`ContentCache`) based on priority and usage.
    - **Local Network Access:** Users within the school can access the full platform via the local network, even without internet.
- **Client-Side Offline Capabilities:**
    - **PWA for Offline Access:** A fully-featured Progressive Web App for mobile and desktop.
    - **Content Download Management:** A robust download manager (`DownloadQueue`) for users to save courses for offline use.
    - **Bandwidth-Conscious Design:** Multiple quality variants for video and other content (`ContentVariant`) to accommodate different network speeds.
    - **User Network Preferences:** Users can control download settings (WiFi-only, data limits, quality preferences).
- **Synchronization:**
    - Delta-based synchronization between client devices, local school servers, and the central cloud database.
    - Scheduled and manual sync options (`ServerSyncLog`, `OfflineSync`).

### Monitoring & Administration
- **Audit Logging:** Comprehensive logging (`AuditLog`) of all critical actions within the system.
- **Notifications:** A system for notifying users about important events (`Notification`).

## OUT OF SCOPE (Phase 1)

- Real-time collaboration features (e.g., live chat, collaborative document editing).
- Gamification (badges, leaderboards, points systems).
- Advanced AI-driven analytics or personalized learning path recommendations.
- Financial and payment processing systems.
- Third-party integrations (e.g., external video conferencing, other LMS platforms).
- Native mobile applications (focus is on the PWA).

# 4. Target Users & Personas

1.  **Student (e.g., "Fara", 12 years old):** Accesses classes on the school's local network. Downloads next week's lessons to her tablet to study at home where there is no internet. Syncs her quiz results and assignment progress when she returns to school.
2.  **Teacher (e.g., "Mr. Jean", 35 years old):** Creates a new math course with video lectures, a practice quiz, and a PDF assignment. Submits it for validation. Later, he grades student submissions and tracks the progress of his entire class.
3.  **Parent (e.g., "Marie", 42 years old):** Logs into the parent portal to see her daughter Fara's recent grades and upcoming assignment due dates.
4.  **School Admin (e.g., "Mrs. Duval", 50 years old):** Sets up the new academic term, creates user accounts for new teachers, and assigns them to their respective classes. Monitors the storage usage on the local school server.
5.  **Educational Manager (e.g., "Dr. Rakoto", 45 years old):** Reviews Mr. Jean's new math course, provides feedback, and approves it for publication, making it available for enrollment.

# 5. Technical Foundation

- **Frontend:** Next.js 14 (App Router) with TypeScript.
- **Backend:** Next.js API Routes.
- **Styling:** shadcn/ui + Tailwind CSS.
- **Database:** PostgreSQL (Neon). The schema is now a comprehensive, relational model designed to support the full LMS functionality.
- **Authentication:** NextAuth.js, adapted for the new granular `UserRole` and profile models.
- **Offline & Caching:**
    - **Client-Side:** PWA with Service Workers and IndexedDB for storing offline content (`OfflineContent`) and managing uploads.
    - **Server-Side:** Local school servers running a lightweight Node.js application to manage the content cache (`ContentCache`) and sync with the cloud.
- **Data Synchronization Strategy:**
    - A three-tiered approach: Client ↔ Local Server ↔ Cloud.
    - Delta-based updates to minimize data transfer.
    - A robust conflict resolution strategy, prioritizing data integrity.
    - Background synchronization with exponential backoff for resilience in poor network conditions.

# 6. Core Features Detailed

- **Comprehensive Course & Content Management:** The platform supports a rich content hierarchy: `Course` → `Section` → `Lecture`. Instructors can build complex learning paths using various `LectureType`s. The `CourseValidation` model ensures a peer-review process, maintaining educational quality before content is published.

- **Multi-Faceted Learning Experience:** Students can engage with a variety of content types, from passive `Video` and `Article` lectures to interactive `Quiz` and `CodingExercise` sessions, and practical `Assignment` and `Project` work.

- **Advanced Assessment & Grading:** The `Quiz` model supports multiple question formats and automated grading. The `Assignment` model facilitates file submissions for manual review. All results are consolidated into the `Grade` model, providing a single source of truth for a student's academic performance.

- **Robust Offline-First Architecture:** The system is designed for resilience. The `SchoolServer` acts as a local source of truth, allowing the school to operate independently of internet connectivity. The PWA client extends this capability, allowing individual users to download content via the `DownloadQueue` and `OfflineContent` models for true "learn anywhere" access. `ContentVariant` and `UserNetworkPreference` models ensure this is done efficiently, respecting bandwidth and data limitations.

- **Granular User & School Management:** The system moves beyond simple user roles to a profile-based architecture (`Student`, `Parent`, `Instructor`, `Admin` models linked to a core `User` account). This allows for tailored experiences and permissions for each stakeholder in the educational process.

- **Contextual Messaging System:** Implement a robust messaging platform enabling direct and group conversations. Crucially, this system supports contextual discussions linked directly to courses or lectures, fostering focused collaboration and clarification around specific learning materials.

# 7. Constraints & Challenges

- **Technical Complexity:** The three-tiered synchronization architecture (client-server-cloud) is inherently complex and requires meticulous design to ensure data consistency and integrity.
- **Hardware & Infrastructure:** The local `SchoolServer` introduces a hardware requirement for participating schools, which needs to be managed and maintained.
- **Data Synchronization:** Handling large volumes of data, especially video, and managing conflicts during synchronization will be a significant engineering challenge.
- **Regional Considerations:** The platform must continue to support multiple languages (French, English, Malagasy) and be culturally adaptable.

# 8. Phase 1 Timeline

The expansion of scope from a simple communication tool to a full-fledged LMS represents a significant increase in complexity. The original timeline is no longer applicable. A new, detailed project plan and timeline must be developed, but a high-level estimate suggests a **9-12 month development cycle** for this phase.

- **Months 1-3: Core Foundation & User Management:** Implement the new database schema, authentication with granular roles, and core user profile management.
- **Months 4-6: Content & Course Management:** Develop the full CRUD lifecycle for courses, sections, and all lecture types. Implement the course validation workflow.
- **Months 7-9: Offline Architecture & Synchronization:** Build and test the local school server, client-side PWA offline capabilities, and the three-way data synchronization logic.
- **Months 10-12: Testing, Pilot & Deployment:** Conduct comprehensive end-to-end testing, run a pilot program with a partner school, and prepare for a phased rollout.

# 9. Success Criteria (MVP for Phase 1)

**Core Functionality:**
- All user roles (`Student`, `Teacher`, `Parent`, `Admin`) are functional with distinct dashboards and permissions.
- Instructors can create, update, and publish a course containing at least video, article, and quiz lectures.
- The course validation workflow is functional.
- Students can enroll in courses, view content, and complete quizzes.
- Parents can view their children's progress and grades.
- **Offline:** Students can download a full course via the PWA and consume all content types while fully offline. Progress made offline is successfully synced back when connectivity is restored.

**Technical Requirements:**
- The local school server can cache course content and serve it to local network clients without an internet connection.
- The PWA is installable and achieves a Lighthouse performance score of 85+.
- Data synchronization between the cloud, local server, and an offline client is successful and verifiable.
